API Monitor — Demo Walkthrough

Not a slide deck — a talk track. Read it top to bottom once before you go in, then let the app do the rest.

Total time ~10 min

1 · The open

~90 sec

Say this before you touch the keyboard.

"So — quick context before I show you this. Right now, if someone on our team wants to know whether an internal API or a partner service is actually up, there's no real way to check besides manually pinging it, or waiting until a customer complains. There's no shared history, no dashboard, nothing that tells you an API's been degrading for the last three days.

That's the gap this closes. It's a synthetic monitoring platform — you register an endpoint once, and from that point on it gets health-checked automatically, forever, on whatever schedule you set. Could be every minute, could be every hour. And everything it finds — uptime, response time, failures — lands on one dashboard anyone on the team can pull up.

And deployment's deliberately boring — the whole backend is two Docker containers, Postgres and Redis, brought up with one command. Nothing external, nothing to license, nothing that needs its own infra ticket. It's meant for whoever's closest to the pain: DevOps first, but developers and QA get the same visibility without having to ask.

Let me just show you, it's faster than explaining it."

2 · Show it live

~6 min

One continuous flow — each beat leads into the next, don't pause for permission.

01

Start from nothing — bring up the stack

terminal → docker compose up -d "Before anything else — this is the entire deployment." (run it, let the two containers come up) "Two containers, Postgres and Redis. That's the whole footprint. The app itself is just a Node process on top of that — nothing else to install, nothing else to provision."

02

Land on the dashboard

open localhost:5173 "And here's the dashboard, completely empty — nothing's registered yet. That's actually the best way to see how this works, so let's add something real and watch it come alive."

03

Add an endpoint

Endpoints → Add Endpoint "I'll give it a name, drop in a real URL, tell it how often to check — every minute is fine for right now — and what a healthy response looks like. Save it." (fill it in as you talk, hit Save) "That's the entire onboarding step. No code, no config file, no deploy."

04

Trigger a check

"It'll check on its own in a minute, but let's not wait — I'll just trigger it." click the ↻ next to the row "And there — status, response time, last checked, all live. In real use that just happens on its own, every minute, for every endpoint you've registered. I'm only doing it by hand so we don't sit here waiting."

05

Open the endpoint's detail page

click into the endpoint "This is where it gets useful over time — every single check ever run against this endpoint gets stored, so 'is it slow' or 'was it down last night' stops being a guess and becomes a graph you can just look at." (point at the response-time and availability charts, flick the 24h/7d/30d toggle once)

06

Show it at scale

Import "Now, one endpoint's easy. What about a team with forty microservices? Two ways in — a CSV if you've already got a list, or this: point it at any team's OpenAPI spec, hit Discover, and every route in it shows up as a checkbox." (paste a Swagger URL, click Discover, let the list populate) "Nobody's hand-typing forty rows into a form."

07

Back to the dashboard

Dashboard "And now it's not empty anymore. Health distribution up here, and down here — this is the one I actually like — every endpoint, sorted worst-first on purpose, so whatever's broken floats straight to the top. And that's not just a percentage, it's 'up for two hours' or 'down for twelve minutes' — how long the current state has actually held."

08

Close on Reports

Reports "Last stop — this is the rollup. Daily numbers, then weekly: fastest services, slowest services, least stable, best availability. Honestly, this is the page I'd bring to a postmortem."

3 · Under the hood

~2 min

"Quick word on how it's actually built, for anyone curious —"

React + Vite UI → Express API → PostgreSQL ↺ node-cron scheduler → any HTTP endpoint
LayerTechWhy this, not the alternative
Frontend ReactTypeScriptTailwind v4Recharts Every chart on screen is real data rendered live — nothing's a screenshot or a mock number.
Data fetching React Query Dashboard and endpoint list refresh themselves every 15 seconds, no polling code to maintain.
Backend ExpressTypeScriptZod Every request is schema-validated before it touches the database — bad input never gets stored.
Scheduler node-cron Ticks every minute, asks "who's due," fires checks in parallel — same loop for 1 endpoint or 500.
Database PostgreSQL Every check ever run is a row — that history is the whole reason the charts and reports exist.
Cache Redis Dashboard summary is cached 30 seconds so a room full of people refreshing doesn't hammer Postgres.
Infra Docker Compose That docker compose up -d from the top of the demo — same command on any internal server, nothing to hand-install.

4 · If they ask

buffer

"Does this hold up past a handful of endpoints?"

"Yes — the scheduler checks every due endpoint in parallel each tick, and the OpenAPI importer just did forty in one click a minute ago."

"What happens when something actually goes down?"

"It's on the dashboard immediately — Recent Failures and the health list both update within the minute. Alerting to Slack or email is the natural next step; I scoped it out deliberately for this first version."

"Can it reach our internal services, not just public sites?"

"Anything reachable from wherever we deploy it — internal network included. That's the point of running it ourselves instead of a third-party monitor."

Land on: "Add an API once, and you're tracking it forever." Then stop talking.
